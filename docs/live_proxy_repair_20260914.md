# 行情代理修复：2026-09-14

## 原因

服务器于 2026-09-12 16:49（北京时间）重启。重启前的 mihomo 服务日志显示
8 月 23 日曾在 127.0.0.1:7893 提供 mixed 代理；重启后的运行配置提供
HTTP 7890、SOCKS 7891、redir 7892，没有 7893 监听。
无法仅凭这些日志确定配置由谁、何时修改。

交易容器的 OKX_PROXY_URL 使用 7890，但 Compose 将行情专用的
OKX_DATA_PROXY_URL 默认写死为 7893。run_all.py 把后者传给股票及加密
补数进程，导致账户查询仍可运行而行情补数持续连接失败。

## 修复

Compose 的数据代理现在依次使用显式 OKX_DATA_PROXY_URL、OKX_PROXY_URL、
默认 http://127.0.0.1:7890。更新 .env.example 说明，保留专用代理覆盖能力。

在确认账户没有仓位、普通挂单后，于北京时间 16:43:43 使用
docker compose up -d --no-build --no-deps okx-quant 应用配置。
运行容器与原镜像一致，没有需要迁移的容器内源代码修改；没有构建新镜像。
原有自动交易配置继续运行。

## 用户补充双代理分工后的最终修复

用户说明实时查询与行情下载原本使用两套订阅。进一步检查发现
/root/clashctl/okx-download/config.json 是独立的 7893 mixed 代理，节点
与已保存的 okx-vpnmiao 订阅匹配。服务器仅启用了主 mihomo.service，
没有独立下载服务，因此仅把数据流量改到主代理并未保留原有分工。
前述主服务端口变化不能完整解释独立下载进程为何未恢复；已确认的
持久化问题是独立下载代理没有 systemd 自启单元。

最终配置：

- 主代理 OKX_PROXY_URL=http://127.0.0.1:7890，保留实时查询用途。
- .env 显式设置 OKX_DATA_PROXY_URL=http://127.0.0.1:7893，恢复喵喵下载。
- 安装并启用 deploy/mihomo-okx-download.service，使用原有下载配置，
  开机启动，异常退出后 5 秒重启。服务只监听 127.0.0.1。
- 原下载配置通过 mihomo -t；7893 的 OKX 股票行情请求返回 code=0。
- 使用原镜像重新应用容器环境。Compose 的代理继承逻辑仍保留，
  但本服务器通过显式覆盖保持双代理分工。

没有查到订阅账单，不能从节点名称确定两套服务的实际价格。

最终双代理验证：16:53:08 股票整轮 167/167 刷新成功、last_error=null；
加密 8 个币种 K 线及指标均补数成功。独立下载服务 active、enabled。
